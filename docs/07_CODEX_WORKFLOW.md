# 07. Работа с Codex и организация репозитория

Codex поддерживает проектные инструкции AGENTS.md [S07]. Официальные материалы также описывают сохраняемые планы выполнения и актуализируемые документы состояния для длинных задач [S08/S09]. Нижеследующая организация — адаптация этих принципов под данный проект, а не обещание автономно восстановить сервер без контроля.

## Структура после исследования

```text
AGENTS.md
README.md
src/

  domain/            # commands, IDs, ruleset contracts
  simulation/        # world, movement, weapons, visibility
  services/          # sessions, lobby, matchmaking
  persistence/       # schema, migrations, ledger
  diagnostics/       # traces, journal, metrics

  packet_inspect/
  load_driver/

  decisions/
```

Это логическое разбиение, не указание заранее создать десятки пустых проектов. Фактические сборочные файлы и команды добавить после выбора стека. Уже написанный рабочий компонент не переписывать только ради соответствия дереву.

## Карточка задачи

Каждая задача содержит исходную проблему, цель, предусловия, разрешённые файлы/пути, контракт, отрицательные сценарии, приёмку, команды, evidence и способ отката. Ограничить масштаб до одного пользовательски/технически проверяемого результата.

Пример хорошей карточки: «Два клиента входят в одну арену; второй видит изменение направления башни первого, подтверждённое сервером; есть логи обоих клиентов и сервера». Пример плохой: «Полностью реализовать сетевой слой, физику и бой».

## План и исполнение

Перед комплексной задачей создать `docs/plans/Pxx_task.md`: контекст, последовательность, ожидаемые артефакты, риски, проверки и критерий завершения. В ходе работы уточнять факты, не менять цель незаметно. Итоговый STATUS ссылается на конкретный test run и commit.

После каждого пользовательского контроля этапа сохранять небольшой commit. Если изменения не проверены, это видно из сообщения и STATUS. Не называть сборку стабильной, пока не выполнена соответствующая матрица.

## Ветки и слияние карточек — решение владельца от 2026-10-07

1. Одна проверяемая карточка — одна ветка `codex/<card-id>-<short-purpose>`,
   например `codex/org-0a-project-hygiene`, `codex/org-0b-test-repair` или
   `codex/p03e-fire-reload`. Многомесячная фаза P03/P06 не является одной
   бесконечной веткой. Следующую карточку начинаем от актуального `main`
   после слияния предыдущей.
2. Первый исторический snapshot сохраняется один раз как
   `baseline-2026-10-07`. Он фиксирует исходники и известный долг проверок,
   не объявляет проект stable/green и не закрывает незавершённую приёмку.
   Коммиты и тег не переписываются. Принятые ранее P03D/P03E опираются на
   отдельные owner receipts, а не на факт попадания кода в baseline.
3. Перед merge нужны применимые проверки текущего head и выполнение критериев
   карточки. Native/UI/управление требуют настоящего native/owner evidence,
   если это предусмотрено карточкой. Unit/build/route-ready не заменяют
   ручную приёмку. Обязательный FAIL/NOT_RUN оставляет карточку в её ветке.
4. Для ORG-0A известные 10 ошибок и 4 пропуска полного Python suite допустимы
   только как сохранённый исходный долг ORG-0B: runtime не меняется, собственная
   организационная приёмка должна пройти. `main` при этом не stable/green.
5. После подтверждения критериев карточка сливается обычным
   `git merge --no-ff <card-branch>` в `main`, затем выполняются обычный push,
   проверка remote SHA и запись evidence. Владелец разрешил этот порядок:
   отдельное разрешение на merge принятой карточки не требуется. Если нужен
   ручной тест, ждём его фактический результат.
6. Для параллельных изменений нужны отдельные worktree/ветки и разделённое
   владение файлами; в одном shared checkout ветки одновременно не переключают.
   Не создавать параллельную работу без отдельной необходимости и авторизации.
7. Запрещены force-push, reset --hard, удаление чужой истории, merge непроверенной
   карточки, изменение защиты remote и публикация client/local/secret/generated
   материалов. Перед push проверяются `git ls-files`, status и allowlist.
   Git identity настраивается только из данных владельца; global config не меняется.
8. PR не обязателен. Если PR создан, он прикрепляется к чату и сохраняет те же
   критерии приёмки. После ORG-0A — отчёт; ORG-0B в этой карточке автоматически
   не начинается.

Текущая фаза и единственный следующий шаг: [ACTIVE_GATE](ACTIVE_GATE.md).

## Параллельная работа

До P03 предпочтителен один агент-интегратор. После фиксации контракта можно независимо разрабатывать ресурсный импорт и unit-тесты правил, не меняя одновременно критические файлы gateway/клиента. Изолировать работы по веткам/рабочим деревьям и передавать интегратору небольшие reviewable изменения.

Нельзя поручить разным агентам несовместимые модели координат, сущностей или времени и рассчитывать, что merge сам их согласует. Общие schemas и ruleset меняются явно.

## Роль разработчика

Разработчик задаёт историческую цель, предоставляет рабочую копию клиента, запускает/проверяет реальный игровой сценарий там, где среда агента этого не позволяет, оценивает управление и принимает архитектурные изменения. Codex исследует доступный код, пишет утилиты/сервер/тесты, запускает доступные проверки и фиксирует доказательства.

Если у агента нет GUI/второго клиента, это не повод имитировать проверку: он формирует точный ручной сценарий и ставит NOT_RUN. Готовность к запуску теста и пройденный тест — разные результаты.

## Формат итогового отчёта

Цель и фактический результат; список изменений; команды; таблица PASS/FAIL/NOT_RUN; evidence; неизвестные параметры; ограничения; способы отката; следующие зависимости. Нельзя завершать только словами «всё должно работать». Один следующий шаг предпочтительнее десяти новых направлений.

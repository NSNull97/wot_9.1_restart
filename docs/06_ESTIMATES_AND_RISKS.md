# 06. Трудоёмкость, мощности и риски

## Основания оценки

Все числа ниже — предварительные инженерные диапазоны, не результаты разработки, нагрузки или статистика чужого проекта. Предполагаются один разработчик с Codex, 20–25 часов собственной вовлечённости в неделю, доступный рабочий клиент, отсутствие необходимости заново разрабатывать графику и узкий первый PvP. Чтение кода, тесты, исследования и исправления входят во время. Работа ботов и массовая поддержка всего контента оцениваются отдельно после первых вертикальных срезов.

Совместимость native-протокола и полноценный самостоятельный сервис — более широкий и неопределённый объём, чем ранний прототип на собственном клиентском адаптере. Эти оценки заменяют оценку адаптерного прототипа для текущей цели.

| Контрольный результат | Суммарные часы от старта | Порядок календарного времени при 20–25 ч/нед |
|---|---:|---|
| P00–P01: исследование и решение | 40–80 | 2–4 недели |
| L1: два клиента в общей арене | 200–450 | 2–5 месяцев |
| L2: ограниченный закрытый PvP | 600–1100 | 6–13 месяцев |
| L3: 15×15 и базовый игровой сервис | 1200–2200 | 12–26 месяцев |
| L4: подготовленная публичная бета | 1800–3000+ | 18–35+ месяцев |

Сроки суммарные, не складываются. Нижние границы предполагают полезные совместимые наработки и отсутствие крупных блокеров; верхние не являются гарантированным пределом. При большем числе часов календарь сокращается не идеально линейно: часть ожиданий и исследовательских ошибок остаётся. Оценку нужно пересчитывать после P01, P03 и P06 по фактической трудоёмкости.

Значительный блокер в транспорте/движке требует нового исследования, а не автоматического заявления о невозможности проекта. Достаточно ли результата L2 для личного использования — отдельное продуктовое решение; L4 не обязательно ждать, чтобы играть закрытой группой.

## Локальная разработка

Предварительно использовать имеющийся ПК: Ryzen 9 5950X, 32 ГБ RAM, RTX 4070 Super. Сначала проверить сервер и один-два реальных клиента, возможность нескольких процессов и фактическое потребление памяти. Не покупать железо до этих измерений. Второй тестовый ПК важен для проверки сетевых предположений, но не обязательно должен быть новым.

64 ГБ памяти — опциональное улучшение только после измерения дефицита при параллельных клиентах, IDE и других проектах. Для серверной архитектуры без рендера GPU не планируется; видеокарта обслуживает клиентские проверки, а не штатную симуляцию сервера.

Разработка клиента — Windows. Linux-сборка сервера проверяется рано, если серверные зависимости действительно доступны; не откладывать обнаружение Windows-only зависимости до аренды Linux-хоста.

## Начальные стенды размещения

| Что проверяем | Предварительная конфигурация для замеров |
|---|---|
| Небольшая комната 2–8 игроков | 2–4 быстрых vCPU, 4–8 ГБ RAM |
| Один бой до 30 участников | 4–6 быстрых vCPU, 8–16 ГБ RAM |
| Несколько параллельных комнат | 8–12 быстрых vCPU, 16–32 ГБ RAM |

Таблица не задаёт гарантированный онлайн. Выделенность CPU, частота, облачный steal, паттерн нагрузки, геометрия карты и стоимость видимости измеряются. В production оставляется запас относительно достигнутого лабораторного максимума.

SSD нужен для пакетов и журналов; объём рассчитывается по фактическому импорту и политике хранения. Несколько десятков гигабайт для первых серверных данных — плановый резерв, а не измеренный размер клиентского архива. Графические ресурсы клиента не нужно автоматически хранить в каждом worker.

## Сеть и бюджет

Пример грубой оценки: 30 объектов × 64 байта × 20 обновлений/с × 30 получателей = 1 152 000 байт/с, около 9,2 Мбит/с полезных данных. В реальной модели фильтрация/дельты могут уменьшить расход, а события, заголовки и повторная доставка — увеличить. Это не прогноз конкретного native-протокола.

Для домашнего стенда проверять стабильность отдачи, входящие соединения, NAT и фактический RTT тестировщиков. Для внешних закрытых тестов лучше отдельный доступный тестовый endpoint после L1. Наиболее ранняя аренда не устраняет риск несовместимого клиента.

Финансовый бюджет делится на инструменты/Codex, временный тестовый хост, production-хост, резервные копии, раздачу проектных обновлений и защиту. Тарифы здесь не зафиксированы: их выбирать по измерениям и условиям регистрации/оплаты непосредственно перед арендой. Не закладывать постоянную публичную инфраструктуру до работающего PvP.

## Реестр рисков

| Риск | Ранний индикатор | Действие |
|---|---|---|
| Native-протокол не совпадает с готовой библиотекой | Клиент не принимает сообщения, .def не объясняет payload | Корпус реальных трасс; узкие кодеки; отдельный прототип; решение по Gateway |
| В ресурсах нет достаточной серверной геометрии | Не совпадают мосты, стены или броневые поверхности | Диагностический импорт одного объекта; исследование формата; не масштабировать контент |
| Jolt не совпадает с клиентским предсказанием | Постоянные коррекции своего танка | Отдельная калибровка контроллера и prediction; не доверять клиентской позиции |
| Не установлена формула старого разброса/фугасов | Разные источники противоречат друг другу | Версионированная спецификация, UNKNOWN/approximate, статистический инструмент |
| UI работает, события теряются | Урон есть, звука нет или он повторяется | Сквозной ID/trace, mapping native-событий, реальный двухклиентный тест |
| Экономика дублирует награды | Повтор результата меняет баланс повторно | Уникальные ключи, транзакции, журнал, fault injection |
| Утечка невидимых противников | Позиция есть в трафике до обнаружения | Серверная фильтрация получателей и payload, тесты побочных каналов |
| Неизвестная безопасность legacy-сети | Неограниченный парсер/слабая авторизация | Threat model, изоляция, bounds, ограничения, закрытый тест до аудита |
| Код создаётся быстрее, чем проверяется | Много «готовых» модулей без evidence | Один этап за запуск, приёмка на реальных клиентах, статус NOT_RUN |
| Публичный сервис сложнее самой комнаты | Сбои обновления, злоупотребления, утраченные данные | Лаунчер и эксплуатация отдельной фазой, restore/rollback упражнения |
| Ограничения на код/ресурсы | Неизвестная лицензия или происхождение | Реестр зависимостей и прав; не включать в публичный пакет до проверки |

Полная юридическая оценка не проводилась. До публичного распространения клиента, игровых ресурсов или стороннего кода нужна отдельная проверка прав и лицензий; факт наличия файла в интернете не даёт ответ на этот вопрос.

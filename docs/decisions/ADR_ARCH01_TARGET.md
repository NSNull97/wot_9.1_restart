# ADR-002 (ARCH-01) — целевая архитектура многопользовательского сервиса

Статус: **ACCEPTED — принят владельцем 2026-10-20**. Дата: 2026-10-20.
Основание: [текущее состояние](../research/ARCH01_CURRENT_STATE.md), [02_ARCHITECTURE](../02_ARCHITECTURE.md),
[ADR-001](ADR_TRANSPORT_AND_STACK.md), [CAPACITY_1000_CCU](../research/CAPACITY_1000_CCU.md).
План перехода: [ARCH01_MIGRATION](../plans/ARCH01_MIGRATION.md).

Всё ниже — **проектное предложение**, не описание внутренностей WG/«Ориона» и не
проверенный факт о клиенте. Транспорт остаётся NATIVE_PRIMARY (ADR-001); ADR не
меняет протокол, исторические характеристики и стек языков.

## Цель и размер

Первый целевой размер: **200 одновременно подключённых игроков (CCU)**, бои 15v15
(30 машин), одна машина-хост для всего, кроме резервной копии БД. Следующий порог
(~1000 CCU) — по модели CAPACITY_1000_CCU, после замеров настоящего боя.

## Решение (предлагается)

Четыре роли процессов, «модульный сервис», не микросервисы:

```text
 клиенты 0.9.1 ──UDP native──► [1] Login/Session Gateway (Rust, 1 процесс)
                                  │ держит все соединения, шифрование, ACK,
                                  │ native-кодирование; без игровой логики
              typed messages      │
      ┌───────────────────────────┼─────────────────────────────┐
      ▼                           ▼                             ▼
 [2] Domain/Account service  [3] Matchmaker/Queue        [4] Battle Worker × N
  (1 долгоживущий процесс;    (в процессе [2] на старте;   (Rust; K арен на процесс,
   Python-сторы сейчас)        правила из конфигурации)     поток на арену; Jolt-сцена
      │ единственный писатель                               рядом — C#-процесс на арену)
      ▼ аккаунт-агрегатов                                       │ итог боя (idempotent)
 PostgreSQL (цель; SQLite в одном процессе — промежуточно) ◄────┘ через [2]
```

1. **Gateway** — только соединения. Владеет native-каналом (framing, шифрование,
   seq/ACK, фрагменты), сопоставляет клиента с `account_id` и маршрутизирует:
   команды ангара → Domain, команды боя → Battle Worker, где сейчас арена игрока.
   Переводит доменные события в native-методы и обратно; ID методов не уходят глубже
   (AGENTS). Ёмкость задаётся числом соединений (цель ≥ 256), **не** размером боя.
   Вход неблокирующий: N параллельных auth-заданий с очередью и лимитом.
2. **Domain/Account service** — один долгоживущий процесс, единственный писатель
   агрегатов аккаунта (инвентарь, экипаж, БК, исследования, резерв машины, итоги боя).
   Каталог загружается один раз при старте. Типизированные команды с идемпотентным
   ключом. Начинаем с существующих Python-сторов (64 тыс. строк не переписывать),
   объединяя версии карточек в одну текущую с миграциями схемы.
3. **Matchmaker/Queue** — очередь «В бой», формирование команд по правилам из
   конфигурации (размер команд, уровни, допуск машин, тайм-аут неполного боя).
   Резервирует машины через Domain и заказывает арену у Battle Worker. На старте —
   модуль процесса Domain (одна точка истины о резервах), отдельный процесс — только
   по измерению.
4. **Battle Worker** — владеет целыми аренами; арена = мир + участники + своя
   Jolt-сцена (C#-процесс рядом, как сейчас). Единственный авторитетный писатель
   состояния боя; в БД не пишет — отдаёт итог в Domain с уникальным ключом
   `(battle_id, account_id)`. Размер арены — параметр (до 30), не константа типа.
   Видимость/interest set считается здесь; Gateway получает уже отфильтрованные
   события для каждого клиента и не знает скрытого.

**Внутренний обмен:** типизированные сообщения поверх локального сокета
(length-prefixed, схема с версией, ограничения размера/частоты/глубины). Язык схемы
(например, JSON Schema → кодогенерация, или protobuf/flatbuffers) выбирается в карточке
CAT-01/DOM-01 по тестам; не HTTP-на-каждую-команду и не порождение процесса.

**Единый источник контрактов.** Один каталог `content/catalog` (машины, модули,
снаряды, места экипажа, допуск в бой, боевой профиль физики/брони) собирается одной
утилитой из закреплённых ресурсов клиента + серверных профилей, имеет версию и SHA-256.
Для каждого языка генерируются данные/типы: Rust (Gateway, Battle Worker), Python
(Domain), JS (сайт/валидаторы), Python 2.7 таблица для client_patch (только UI-подсказки,
сервер остаётся авторитетом). Каждый процесс при старте сверяет хеш каталога и
отказывается работать с чужим. Допуск машины в бой — поле данных
(`battle_admission`), а не список в коде. Сверка «все потребители согласны» — тест.

**Постоянные данные.** Цель — PostgreSQL, один писатель на агрегат (Domain для
аккаунта; сайт пишет только identity). Идемпотентные итоги и леджер транзакций из
02_ARCHITECTURE. Промежуточно — SQLite (WAL) **внутри одного процесса Domain**:
для 200 CCU это допустимо (INFERRED: ~3–5 записей/с), а переход на PostgreSQL — когда
нужны второй хост, онлайн-бэкап/реплика или несколько писателей. Общий SQLite-файл
между процессами/машинами запрещён (как и в 02_ARCHITECTURE).

## Оценка для 200 CCU (INFERRED, замеры — в плане)

| Величина | Расчёт | Итог |
|---|---|---|
| Игроков в бою | 200 × 60–70 % | 120–140 |
| Арен 15v15 | 140 / (30 × 0,8 заполнения) + 2 резервных | 6 + 2 = **8** |
| Процессов Battle Worker | 2 × 4 арены (или 1 × 8) | 2 |
| Jolt-процессов | по одному на арену | 8 |
| CPU боя | 8 × 0,3–0,6 ядра (10–20 CPU-мс/шаг при 30 Гц — допущение CAPACITY_1000_CCU) | 2,5–5 ядер |
| Входы после рестарта | 200 за ~5 мин | ~0,7 вх./с — нужен вход < 1 с и параллельно ≥ 4 |
| Доменные операции | 200 × ~1–2 оп./мин | 3–7 оп./с (сейчас предел ~0,5) |
| Итоги боёв | 140 / ~600 с | ~0,25 записи/с, пачками по 30 |
| Исходящий трафик | 140 × 50 кбит/с × 1,25 | ~9 Мбит/с |

Вывод: для 200 CCU хватает **одного хоста** класса 8–16 ядер / 32–64 ГБ, если сняты
программные пределы. Узкие места сегодня — вход (11 с, по одному), доменные операции
(0,5 оп/с), одна арена на 6 машин; железо их не снимает.

## Отказы и восстановление

| Отказ | Поведение |
|---|---|
| Ошибка мира/физики арены | закрывается одна арена (поведение STAB-01 сохраняется), игроки в ангар, резервы снимает Domain |
| Падение процесса Battle Worker | теряются его арены (живой перенос боя не делаем); Domain по аренде (lease) с тайм-аутом снимает резервы; Gateway возвращает игроков в ангар |
| Падение Domain | Gateway отвечает «недоступно» на команды ангара, бой продолжается; итоги ждут в очереди worker'а и доставляются повторно (идемпотентно) |
| Падение Gateway | все клиенты отключаются, повторный вход; арены без игроков доигрываются/закрываются по тайм-ауту |
| Потеря БД | резервная копия + WAL; RPO/RTO выбирает владелец до публичного запуска |

## Границы безопасности

Наружу — только UDP-порты Gateway и HTTPS сайта. Domain, Matchmaker, Battle Worker,
Jolt и БД слушают только loopback/частную сеть с общим секретом процесса. Gateway
подставляет `account_id` из сессии; идентификатор игрока в payload не доверяется.
Все внутренние парсеры ограничивают размер/глубину/частоту (AGENTS). Сайт не пишет в
игровые агрегаты; административный доступ отдельно.

## Альтернативы

- **A. Один Rust-процесс «Gateway + арены в потоках» + Domain-процесс.** Меньше
  переходов, проще деплой, ближе к сегодняшнему коду. Минусы: перезапуск/паника любого
  кода роняет все соединения и бои; выкладка боевого кода = разрыв ангара. *Используется
  как промежуточный шаг миграции* (ARENA-01), разделение на Gateway и Battle Worker — когда
  арены надёжно изолированы интерфейсом сообщений.
- **B. Микросервисы/оркестратор (Kubernetes, Agones) с отдельными сервисами на
  каждую функцию.** Даёт автомасштаб, но для 200–1000 CCU и одного разработчика стоимость
  эксплуатации и сетевых переходов выше пользы; native-сессию между сервисами всё равно
  держит один Gateway. Отклоняется до замеров, показывающих нехватку одного-трёх хостов.

## Когда (не) выносить на отдельные машины

- **Не выносить**, пока один хост держит измеренную нагрузку с запасом (≤ 60 % CPU в
  вечернем пике, p99 шага < дедлайна). 200 CCU по оценке — один хост.
- **Первым выносится Battle Worker** (вместе со своими Jolt-процессами): нужен лишь адрес
  Gateway и Domain; это требует доказать, что Gateway проксирует base-канал (клиент не
  переподключается — поведение #717 при смене адреса UNKNOWN).
- **Вторым — БД (PostgreSQL)**: при необходимости реплики/бэкапа без простоя.
- Gateway и Domain разносить на разные хосты — только при измеренной нехватке.
- Распределять одну арену по машинам — не предлагается.

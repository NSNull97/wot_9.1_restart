## Цель карточки

Ввести профиль правил как данные, **не меняя ни одного числа и ни одного исхода выстрела**: все нынешние константы
становятся значениями профиля с пометкой `test_lab`/`requires_verification`. Законы 2.0 (±25 %, 10 калибров, HESH,
Dual Dispersion…) — следующие карточки, они будут менять только профиль и код законов, а не механику профиля.

## Шаги

1. **Схема и слои** — `config/shell_rules/`: файлы слоёв в порядке 2.0 (`server_defaults` → `historical_0_9_1` →
   `classic_plus` → тип снаряда → определение снаряда → орудие/машина → режим игры). Формат JSON (см. вопрос 1).
   Закрытая схема: неизвестный ключ, тип или выход за границу — отказ; у каждого значения `status`
   (`verified_091` / `test_lab` / `requires_verification` / `experimental`) и источник.
2. **Сборка снимка** — `tools/shell_rules.py` (слияние слоёв, проверка, канонический JSON, `rulesHash` = SHA-256 байтов,
   `configVersion` — целое из профиля) и генерируемая привязка для Rust (как CAT-01: встроенные байты + закреплённый
   хеш). Команды `build` / `check`, тесты слияния и отказов.
3. **Шлюз** — `shared/shell_rules.rs`: загрузка встроенного профиля (или файла стенда с закреплённым SHA, см. вопрос 2),
   неизменяемый `Arc<RulesSnapshot>` на бой при выборе мира; `p06t_damage.rs` и `track_pass` берут числа из снимка
   вместо констант. Печать `SHELL_RULES_BOUND configVersion=… rulesHash=…` при старте и в `P08B_WORLD_SELECTED`.
   Смена профиля действует только на новые бои (процесс шлюза грузит профиль один раз; живой подмены нет).
4. **Трасса выстрела** — при включённой диагностике стенда: JSONL на бой (`shotId`, `battleId`, `rulesHash`, снаряд и
   орудие, дистанция, слои/нормали, нормализация, эффективная броня, остаток, решение, урон), с лимитами размера.
   Поля разброса/сведения/RNG — пустые до DISP-01 и карточки пробития (явно `null`, не выдумываются).
5. **Повтор** — `sr-gateway shot-replay <trace.jsonl>`: пересчёт каждого решения из записанных входов тем же снимком
   правил, отчёт о расхождениях (ожидается 0). Тест Rust на записанной трассе.
6. Тесты: Rust — профиль даёт те же `Resolution` байт-в-байт, что константы `main` (таблица случаев по всем семействам,
   рикошет, 2×/3×, дистанции, гусеница, HE); Python — схема и слияние. Gate шлюза и Python-набор D: = база.
   Бой владельца — короткий контроль на стенде (поведение не должно измениться).

## Вопросы владельцу

1. **Формат профиля** — в 2.0 пример на YAML. Предлагаю JSON: без новой зависимости и небезопасного разбора,
   канонические байты для `rulesHash`. YAML — только если нужен ручной редактор (тогда отдельный проверенный разборщик).
2. **Где выбирается профиль** — (а) встроен в сборку шлюза (как каталоги; смена = новая сборка), (б) файл стенда с
   закреплённым SHA в `gateway.json`. Предлагаю (а) сейчас, (б) — когда появится второй профиль.
3. **Запись в итоги боя** — `rulesHash`/`configVersion` сейчас идут в журнал шлюза и трассу. Добавлять их в итоги
   боя Domain — отдельный шаг со схемой итогов (предлагаю после SHELL-CFG).

Решения владельца 05.11 («Yes, recommended»): 1 — JSON; 2 — профиль встроен в сборку шлюза; 3 — запись в итоги
боя Domain после SHELL-CFG отдельным шагом.

## Не входит

Изменение чисел и законов, RNG ±25 %, правила 10 калибров, HESH, сплэш 2.0, Dual Dispersion, модули — карточки
пробития по слоям, SHELL-03, SHELL-04, DISP-01. Калибр 182 — в карточке пробития по слоям.

## Риски

- Трасса на 30 машин: лимит записей и размера файла на бой, чтобы не нагружать диск.

# BW-01 — Battle Worker отдельным процессом

Ветка `codex/bw-01-on-main` от main `d0a9b9e` (VIS-PERF, STAB-02, RES-30, MM-01, POSTMORTEM-01, NET-01, AV-01):
перенос ветки `codex/bw-01-battle-worker` (`ee98629`, от `c76fd62`) одним коммитом + журналы NET-01 в кодеке
(раздел «Перенос на main» ниже). Строка 9 [ARCH01_MIGRATION](ARCH01_MIGRATION.md); основание — [ADR-002](../decisions/ADR_ARCH01_TARGET.md),
[ARENA-01](ARENA01_MULTI_ARENA.md) (typed-интерфейс шага), [STAB-02](STAB02_BATTLE_CONTAINMENT.md) (`contain_arena`).
Метки — как в AGENTS. Не вливать и не пушить.

## Что есть (VERIFIED, `c76fd62`)

- Шаг арены — `arena::Arena::handle(Command::Step{now,start})` → `advance_battle(&mut world,&mut integrated,now,start)`
  → `Event::{Stepped,Failed{stage,error}}` (`shared/server_arena.rs`). Всё остальное (вход, посадка, ввод клиентов,
  публикация, итоги, сброс, containment) читает и меняет `arena.world` в потоке шлюза между шагами.
- `IntegratedRuntime` (Jolt: `BatchRuntime` = один C#-процесс сцены на бой, старт асинхронный через поток) создаётся
  `BattleTemplate::runtime(map)` при `select`/`replace`; запускается и шагает только внутри `advance_battle`.
  Шлюз вне шага читает у него `ready_for_native()`/`blocked()` (публикация, вход ботов).
- `World` — `Clone`, ≈ 40 полей, 109 типов в замыкании (оружие, устройства, журналы урона/контактов, видимость,
  итоги, боты), `Instant` в состояниях, `Arc` на неизменяемые ресурсы (геометрия, рельеф, препятствия, каталог).
  `serde_derive` в офлайн-кеше cargo нет (есть только `serde`/`serde_json`).
- Глобальное состояние шага: встроенные таблицы (`OnceLock` с проверкой SHA) и флаг `CATALOG_V1` (из `gateway.json`).

## Решение

1. **Граница.** Worker = тот же `sr-gateway.exe` в режиме `bw01-battle-worker` (без конфигурации и сокетов
   клиентов). Он владеет Jolt-рантаймом арены и выполняет `advance_battle`. `World` между шагами остаётся в шлюзе
   (членство, ввод, публикация, итоги, containment не меняются); на каждый шаг шлюз отправляет мир, worker
   возвращает мир после шага и `native_ready`/`blocked` своего рантайма. Это перенос ровно интерфейса ARENA-01
   (`Command::Step` → `Event`), без переноса публикации (вне карточки).
2. **Кодек** `crate::bw_wire` (бинарный, только для пары «этот шлюз ↔ свой worker»): трейт `Wire`; impl для 109 типов
   генерирует `tools/bw01_wire_gen.py` (список — `tools/bw01_wire_types.json`) рядом с типом, с исчерпывающей
   деструктуризацией — новое поле без кодека не компилируется. `Instant` — знаковые наносекунды от якоря стороны
   (worker берёт якорь при рукопожатии; туда-обратно — то же значение). `Arc` — содержимое один раз на соединение,
   дальше id; указатели сохраняются на обеих сторонах. `GeneratedId` проверяется по реестру процесса.
3. **Рантайм в worker.** Шлюз передаёт спецификацию своего (не запускаемого в режиме worker) объекта
   `IntegratedRuntime`: поколение, карта, пул, removal, catalog, общие ресурсы сцены. Поколение меняется при каждом
   `select`/`replace` — worker пересоздаёт рантайм (старый Jolt-процесс закрывается), как сброс в процессе.
4. **IPC** — TCP `127.0.0.1:0`, порт аргументом, одноразовый токен 32 байта — через stdin ребёнка (не в командной
   строке); проверка сборки (SHA-256 exe) в рукопожатии. Кадр: magic, вид, длина; пределы: кадр ≤ 256 МиБ
   (ресурсы карты — один раз), длины последовательностей ≤ остатку кадра и 2^24, таблица `Arc` ≤ 65536, JSON ≤ 1 МиБ;
   время: ответ на шаг ≤ `step_timeout_ms` (по умолчанию 2000), первый шаг соединения (ресурсы) ≤ `startup_timeout_ms`
   (30000), рукопожатие ≤ 10 с. Worker сам выходит при EOF/ошибке сокета.
5. **Отказ worker'а** (EOF, ошибка кадра, тайм-аут, код выхода): процесс добивается, арена — `contain_arena` STAB-02 с
   этапом `battle_worker_lost` на последнем мире шлюза (до шага): игроки — терминал и возврат в ангар, резервы —
   writer, мир — сброс из шаблона; следующий шаг поднимает новый worker. Ошибка/паника шага внутри worker —
   `Failed{stage}` с миром после неудачного шага, как в процессе (`world_step`/`world_step_panic`).
6. **Конфиг** `gateway.json`: `"battle_worker": {"version":1}` (+ необязательные `step_timeout_ms` 100..60000,
   `startup_timeout_ms` 1000..300000). Требует `profile13_battle`; несовместим с `training_rooms` и `p08b_owner_battle_hold`
   (их хосты держат рантайм в потоке шлюза). Без ключа — прежний путь, без новых строк в журнале. Строка запуска
   `BW01_BATTLE_WORKER arenas=K step_timeout_ms=… startup_timeout_ms=…`.
7. K арен = K worker'ов; шлюз рассылает шаги всем и потом собирает ответы (параллельно, как потоки ARENA-01).

Вне карточки: перенос публикации/видимости в worker, дельта-кодирование мира, несколько арен в одном worker,
Linux, native-проверка.

## Проверки

| Проверка | Как |
|---|---|
| Кодек: границы, `Instant`, `Arc` | unit `bw_wire` |
| Шаги in-process и worker совпадают | один и тот же бой (настоящая сцена Jolt, 1+29 машин с ботами) шагается параллельно в процессе и через worker с одинаковыми `now`; сравнение закодированного мира после каждого шага |
| kill worker во время боя | живой бой через worker → `taskkill /F` → containment, шлюз/ангар живы, резерв снят |
| повторный бой | после kill — следующий бой на новом worker стартует и шагает |
| 30 мест через worker | арена 30 машин (1 + 29 ботов) N секунд через worker без ошибок |
| Наборы шлюза и Python против `c76fd62` | множества FAIL совпадают |
| Release-бенч 1+29 в обоих режимах | шаг p50/p99, CPU шлюза/worker/Jolt, RSS |
| Native | **NOT_RUN** (по заданию) |

## Итог (2026-10-29)

Коммиты ветки: `45baf05` (кодек, worker, конфиг), `8c43d7c` (тест kill/повторного боя), `457b4cb` (спецификация
рантайма один раз на поколение, бенч через worker), затем итог (этот коммит).

Реализовано по решению выше. Уточнения по ходу:
- Спецификация рантайма сначала шла по значению на каждом шаге (каталог разрушаемых объектов ≈ 125 КБ/шаг) —
  теперь полная спецификация только при новом поколении, дальше — номер поколения.

- Простаивающая арена (мир не начат, нет старта) не шлёт мир: этот шаг — no-op в любом процессе; новый worker
  один раз получает мир сразу (ресурсы карты заранее).
- Тестовый бинарь не имеет `main` шлюза: worker в тестах — ignored-тест `bw01_worker_process_entry` того же бинаря.

## Перенос на main `d0a9b9e` (2026-10-29)

Ветка `codex/bw-01-on-main` = main `d0a9b9e` + `git merge --squash ee98629` одним коммитом. Конфликты: `identity.rs`
(рядом `pose_delivery` NET-01 и `battle_worker` — оба поля), `bots.rs` (поле `pairing` MM-01; кодек перегенерирован
`tools/bw01_wire_gen.py apply`), `server.rs` (замер `step_started` NET-01 вокруг шага + выбор worker/в процессе), STATUS.

- **Журналы NET-01 в кодеке.** `World` теперь держит `Journal<T>` (copy-on-write). Кодек передаёт журнал
  приращением: у обеих сторон соединения для k-го журнала кадра хранится его последнее пересёкшее значение; если новое
  начинается с него — идут только добавленные строки (тег 1 + длина базы + хвост), иначе журнал целиком (тег 0).
  Приёмник отказывает, если базы такой длины у него нет. Ошибка кодирования или приёма — потеря worker'а (как раньше),
  поэтому таблицы сторон не расходятся. Unit `bw01_wire_journal_crosses_its_appended_rows_and_whole_when_it_changed`.
- `pose_delivery` и MM-01 шага не касаются (публикация и подбор — в шлюзе); worker ставится всем аренам при запуске,
  арены MM-01 не пересоздаются. В бенче NET-01 — `reliable-burst-v2`.
- Бенч NET-01 (`net01_bench_pose_delivery`) получил `NET01_BENCH_WORKER=1` (шаг через worker), CPU процессов и
  размер кадров в отчёте.

## Шаги для стенда (владелец)

1. Собрать release-шлюз из `codex/bw-01-on-main` (`python -B -X utf8 server/build.py gateway --release --out
   local/build/server/<новый>`), поставить на стенд копией (прежний exe рядом). Worker — тот же exe.
2. В `gateway.json` добавить `"battle_worker": {"version":1}`; в журнале запуска — `BW01_BATTLE_WORKER arenas=K …`,
   затем `BW01_WORKER_STARTED pid=…` на каждую арену.
3. Бой; затем во время следующего боя `taskkill /F /PID <pid worker'а>` → в журнале `BW01_WORKER_LOST`, строки STAB-02,
   игроки в ангаре, машины свободны; повторный бой стартует (`BW01_WORKER_STARTED` с новым pid).
4. Откат: убрать ключ `battle_worker` из `gateway.json` и перезапустить шлюз (арены снова в процессе шлюза); либо
   вернуть прежний exe. Схемы, БД и клиент не меняются.

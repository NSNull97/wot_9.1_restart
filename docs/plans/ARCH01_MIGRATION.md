# ARCH-01: план перехода к целевой архитектуре (предложение)

Статус: **принят владельцем 2026-10-20** вместе с [ADR-002](../decisions/ADR_ARCH01_TARGET.md).
Исходное состояние: [ARCH01_CURRENT_STATE](../research/ARCH01_CURRENT_STATE.md).

Принцип — strangler: каждый шаг заменяет одно узкое место, оставляя остальное
работать; одна карточка = одна ветка `codex/<card>-<purpose>`; у каждого шага есть
откат (флаг конфигурации или прежний путь, пока новый не принят) и приёмка.
Native-приёмку закрывает только владелец. Нагрузочные тесты с синтетическими
клиентами — отдельная метка: они не доказывают native-игру (AGENTS).

## Порядок

| # | Карточка | Что меняется | Приёмка (авто → владелец) | Откат |
|---|---|---|---|---|
| 1 | **BRIDGE-01** (в работе) — постоянные Python-воркеры + кеш каталога | bridge держит пул долгоживущих воркеров; `load_catalog` один раз на воркер | latency read-only операции < 300 мс (сейчас ~4 с); `p08b_restart_cas_composition02` PASS в полном gate под нагрузкой → владелец: ангар, покупки, экипаж как раньше | флаг bridge: прежний spawn-на-запрос |
| 2 | **LOGIN-01** (в работе: `codex/full-test-pending-login-queue`) — очередь входа, затем параллельные входы | сейчас: ожидание вместо 73, пока укладываемся в окно клиента; затем ≥ 4 одновременных auth-job, вход не блокирован боем/`ammo_job` | unit + замер времени входа после шага 1 → владелец: два клиента входят одновременно без «сервер не готов» | флаг очереди; прежний одиночный `auth` |

| 4 | **CREW-ANY** — экипаж и БК для любой машины | UI экипажа/БК в client_patch и сторы читают места/снаряды из каталога; ёмкость танкистов > 16 (миграция схемы v2) | тесты сторов на 374 машинах каталога → владелец: купить Т-26, нанять экипаж и загрузить БК из UI, бой | миграция v2 с обратной миграцией на копии БД |
| 5 | **DOM-01** — Domain service | воркеры шага 1 становятся одним долгоживущим процессом с типизированными командами; цепочка сторов `p04d…p04k` сводится в одну текущую версию с миграциями; Gateway вызывает Domain напрямую (bridge — только сайт/identity) | идемпотентность команд (повтор = тот же ответ), один писатель SQLite → владелец: полный ангарный сценарий | Gateway-флаг: прежний HTTP через bridge |
| 6 | **GW-01** — ёмкость Gateway | `Table.capacity` отделена от размера боя (цель 256 соединений); ангарные игроки не занимают места арены | синтетический native-login клиент: 200 входов/выходов, без 73, память/CPU Gateway замерены → владелец: 2 реальных клиента + синтетика | конфиг `capacity` |
| 7 | **ARENA-01** — арена как объект, несколько арен в процессе | `World` + участники + Jolt-сцена → `Arena`; K арен на потоках внутри процесса (альтернатива A из ADR); `MAX_ACTORS`/`CAPACITY` → параметр размера арены (до 30); typed-интерфейс Gateway↔Arena | замер CPU-мс/шаг, p99, RSS для 30 машин; 2–4 одновременные арены без взаимного влияния; ошибка одной арены не трогает другие → владелец: два параллельных боя | одна арена = прежний путь |

| 10 | **PG-01** — PostgreSQL | хранилище Domain за интерфейсом стора: SQLite → PostgreSQL; леджер и идемпотентные итоги; бэкап/восстановление | миграция копии стенда туда и обратно, тесты сторов на обеих СУБД | конфиг выбора СУБД, SQLite-копия |
| 11 | **NET-02 / LOAD-200** | внешние адреса, брандмауэр, синтетика 200 CCU + живые клиенты | замеры по [CAPACITY_1000_CCU](../research/CAPACITY_1000_CCU.md) на одном хосте → владелец: игра с двух ПК | — |

Шаги 1–2 уже идут в других сессиях; ARCH-01 лишь фиксирует их место. **«Экипаж и БК
для любой машины» (CREW-ANY) идёт после CAT-01**, иначе он добавит шестую копию
справочника. Шаги 6 и 3/4 независимы и могут идти параллельно разными ветками.
Шаги 9–10 могут ждать: для 200 CCU на одном хосте достаточно шагов 1–8 (INFERRED).

## Связь с текущим IMPLEMENTATION_ORDER

- P10B (тренировочная комната на N) — частный случай MM-01; не развивать отдельно
  после принятия ADR.
- NET-02 — после GW-01 (иначе внешняя сеть упрётся в 2 места).
- Хвост (микролаг, склад, оборудование, P04L) — независим; можно брать между шагами.
- Причина пауз цикла Gateway (UNKNOWN) — проверить в ARENA-01: разнос арен и сети
  по потокам должен её проявить или устранить.

## Что не делаем

Не переписываем Python-домен на другой язык без замера; не вводим Kubernetes,
брокер сообщений или отдельный сервис на каждую функцию; не делаем живой перенос боя
между процессами; не меняем native-протокол.

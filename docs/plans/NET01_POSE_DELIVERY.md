# NET-01 — доставка поз и измеримость шага в бою 1+29

Ветка `codex/net-01-pose-delivery` от `c76fd62` (`integrate/ft15-20261029` = main + VIS-PERF + STAB-02 + RES-30 + MM-01).
Повод: бой владельца 29.10 (стенд -11, 1 игрок + 29 ботов, Малиновка) — «слайд-шоу» поз и задержка выстрелов.

## Факты до изменения

- Лог `full-test-20261027-11/gateway-20261029-015504.stdout.log`, сессия 1 (OBSERVED): позы каждый тик на тиках
  1300–1900; дальше `SHARED_SNAPSHOT` 71–235 на 300 тиков, промежутки до 30 тиков. Сессия 2 (короткая) — без провалов.
  `CHANNEL_ACK pending` среднее 3,1, максимум 8, selective ACK нет (потерь нет — localhost).
- Код (VERIFIED, `server.rs`): позы — надёжные тела окна `Window` (8 × 512 Б, повтор 700 мс) и ставятся только при
  `tx.len() < 4`; при 14+ видимых машинах поза — 2–3 тела. Главный цикл отправляет **одно** надёжное тело на сессию за
  итерацию (`tx.due` один раз), итерация = шаг арены + публикация + 5 мс сна. INFERRED: при шаге 30–65 мс
  пропускная способность ≈ 2–3 тела за тик домена < 3 тела поз + выстрелы → окно полно → позы пропускаются.
  Это совпадает с ростом провалов вместе с числом видимых машин (с тика ~1900).
- Стартовый лаг (тики 1400–1700) этим не объясняется: позы шли каждый тик. Времени в логе нет — нужна метрика.

## Исследование: как родной сервер шлёт позы

- VERIFIED (`res/scripts/entity_defs/vehicle.def`, SHA-256 `08dc1e6b…1297`, packed XML декодирован `tools/packed_xml.py`):
  секция `<Volatile>` = `position, yaw, roll, pitch`; `avatar.def` (`38cf983d…f74d`) — `<Volatile> position`.
  Позы машин в 0.9.1 — volatile-данные BigWorld, которые идут сообщениями `avatarUpdate*` (0x15 — P02_ARENA_MOVEMENT).
- VERIFIED (P02_SERVER_RELIABLE): клиент сам шлёт на канале ненадёжные пакеты `0x0448` (без бита 0x10), а наш сервер
  часами шлёт клиенту канальные пакеты `0x0408` (только cumulative ACK, без sequence) — клиент их принимает.
  Надёжные номера клиента непрерывны (сервер отвергает дыру `n > rx`), значит ненадёжные пакеты не занимают номера
  надёжных.
- INFERRED: родной BigWorld-сервер слал volatile-обновления ненадёжно (обновление вытесняет предыдущее). Строки
  Mercury в `WorldOfTanks.exe` (SHA-256 `86f5e351…04ed`) вырезаны — приёмник клиента статически не подтверждён.
- UNKNOWN: примет ли клиент сообщения в теле пакета `0x0408` (с непустым телом такой пакет клиенту ещё не слали).
  Проверка — только бой владельца. Поэтому режим включается ключом и откатывается удалением ключа.

## Решение

Ключ `gateway.json` `pose_delivery` (нет ключа — прежний путь байт в байт):
- `"reliable-burst-v1"` — позы прежние (надёжно, `< 4`), но цикл отправляет **все** готовые надёжные тела окна за итерацию.
- `"latest-unreliable-v1"` — то же + позы уходят вне окна пакетом `0x0408` (тело + cumulative ACK, без sequence):
  только поза последнего тика, неотправленная поза заменяется свежей, повторов нет. Надёжное окно — только
  выстрелы/попадания/создания. Поза только для машин, чьё создание клиент уже подтвердил (как прежде).
  Требует `visibility_v1`. Порядок в итерации: сначала надёжные тела, потом поза.

Измерения (всегда, раз в 10 с, только при идущем бое): `NET01_STEP_STATS` — длительность итерации цикла, шага арен,
публикации, промежуток между тиками домена (p50/p95/p99/max); `NET01_SESSION_STATS` — ожидание ACK от первой отправки,
ожидание тела в окне до первой отправки, max pending/outbox, промежутки поз в тиках, число пакетов поз.

## Проверки

1. Unit: формат `0x0408` с телом (разбор нашим парсером), «только свежая» поза, позы не занимают окно, выстрел
   проходит при полном потоке поз, ключ конфигурации, отправка всех надёжных тел.
2. Release-бенч 1+29 (Прохоровка, Jolt, боты) с сессией игрока и моделью клиента (ACK по кадрам, подвисания):
   промежутки поз у клиента и ожидание надёжных тел до/после для трёх режимов.
3. Набор шлюза против `c76fd62` в одной среде: множество FAIL равно.
4. Native: бой владельца на стенде — NOT_RUN в этой сессии.

Выводы: (VERIFIED бенчем) в прежнем режиме позы теряют тики уже при шаге 40–46 мс из-за «одно надёжное тело за
итерацию» и порога `< 4`, надёжные тела (выстрелы) ждут в окне до 100–230 мс; `reliable-burst-v1` это снимает без
изменения формата пакетов; `latest-unreliable-v1` вдобавок не держит устаревших поз после подвисания клиента.

### Шаги для стенда (владелец)

1. Сборка release из этой ветки (`python -B -X utf8 server/build.py gateway --release --out local/build/server/<dir>`).
2. Сначала `"pose_delivery": "reliable-burst-v1"` (формат пакетов прежний) — бой 1+29; затем
   `"latest-unreliable-v1"` (новый для клиента пакет `0x0408` с телом — UNKNOWN до этого боя).
3. Признак отказа клиента от ненадёжных поз: машины стоят/не двигаются при идущих `NET01_SESSION_STATS pose_packets>0`
   — откат на `reliable-burst-v1` или удалить ключ.
4. В логе: `NET01_POSE_DELIVERY mode=…`, каждые 10 с `NET01_STEP_STATS` (цикл, шаг, публикация, интервал тиков) и
   `NET01_SESSION_STATS` (ожидание ACK, ожидание в окне, пробелы поз).

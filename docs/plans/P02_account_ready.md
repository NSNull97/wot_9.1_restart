# P02 — готовность минимального native Account

2026-10-04. Владелец: «давай, доведем акк до готовности».
Продолжение после подтверждённого wire creation и bootstrap FAIL.

Цель карточки: original Account constructor, onBecomePlayer и onBecomeNonPlayer
исполняются без исключений; необходимые начальные запросы установлены по
настоящему клиенту и получают корректные ограниченные ответы своего сервера;
повторный вход/выход не оставляет состояние предыдущего аккаунта.
Готовность относится к минимальному Account/session контракту P02.
Штатный ангар, арена, экономика и интеграция веб-регистрации — отдельные контракты.

1. Сохранить 100 собственных исходных файлов и local config, сверить состояние
   клиента с предыдущим полным manifest. Не затрагивать web/ и original.
2. Прочитать original Settings/game/Account и зависимые bytecode records.
   Поднять только реально необходимые родные компоненты в isolated profile.
   Account классы/обработчики не подменять; локальные entities не создавать.
3. Последовательно исследовать ошибки bootstrap, serverSettings и реальные
   исходящие сообщения. Номера RPC/форматы не угадывать, PYTHON/pickle вход
   не исполнять; новый parser/ответ ограничить подтверждённым срезом.
4. Неподдержанные функции не маскировать успешными заглушками. Собственное
   состояние сервера может быть пустым только как настоящее явно заданное
   состояние тестового аккаунта, не как доказательство полной экономики.
5. Запустить положительные и отрицательные native cases, regression, проверить
   полный rollback и hashes. Обновить STATUS/отчёт/неизвестные/команды.

Evidence: `local/evidence/20261004-p02-account-ready/`. Исходники до изменений:
`project-before.zip`, `project-before.json`; local config сохранён отдельно.
Каждый client run — отдельный ledger/backup/restore. Все endpoints loopback;
аккаунт/ключи только свои. Системное отсутствие внешних соединений не заявлять
без отдельного измерения; компоненты с внешними endpoint не инициализировать
без исследования их конфигурации. Не переходить к P03.

Если достигнут лишь поднабор приёмки, отметить его отдельно и сохранить
конкретный следующий blocker; отсутствие traceback само по себе не доказывает
синхронизацию данных Account или готовность игрового сервиса.

Уточнение по результатам исследования: EXE добавляет исходный CompanyName /
ProductName к абсолютному engine preference path. Для изоляции Python caches
применён узкий diagnostic getter redirect в новый research/p01_profile;
исходный Account и его методы неизменны. Штатное native сохранение preferences
этим не проверяется. Метод onStreamComplete делегируется оригинальному game.
Публичные имена владельца зафиксированы в NAMING; EXE/IDs не переименовываются.
